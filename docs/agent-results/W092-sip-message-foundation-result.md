## 4. Ce poate trimite clientul

SIP MESSAGE requests with:
- **Content-Type**: `text/plain`, `text/html`, or `message/cpim` (CPIM requires "Enable CPIM").
- **Body**: any UTF-8 text, including large bodies (tested at 5 KB); no truncation.
- **Optional IMDN request**: adds `Message-ID` + `Disposition-Notification: positive-delivery, positive-display` headers only — no IMDN document is generated by sending a request.
- **Destination**: whatever SIP URI the user types into the compose field, validated/normalized via the existing `SipUriNormalizer` (no hardcoded IPs/domains/users/passwords/URIs anywhere in this code).

Sending requires "Enable SIP MESSAGE" to be checked and a registered/active
SIP account; it is fire-and-forget (submits to PJSIP's transaction layer and
returns immediately — does not block the UI thread waiting for a response).

## 5. Ce poate primi clientul

No new inbound code was written. `PjsipTraceModule` (Task W090) already taps
every raw SIP request/response at the PJSIP transport layer, method-agnostic,
so an incoming SIP MESSAGE is captured automatically and flows through the
unmodified `MessagingDiagnosticsStore → MessagingEventStore` pipeline exactly
like any other captured message — it appears live in the Messaging
Diagnostics table (and the SIP Ladder, which already displayed MESSAGE
traffic since Task W090). pjsua's default UA behavior auto-responds `200 OK`
at the SIP level since no application-level `Account::onInstantMessage`
callback was registered; there is no dedicated "new message" app-level
notification hook yet (see limitations).

## 6. Cum se generează CPIM

`CpimBuilder::build()` produces:

```
From: <sender URI>
To: <recipient URI>
DateTime: <ISO 8601 timestamp>
Content-Type: text/plain; charset=utf-8

<user-entered body, unmodified>
```

The user only ever types the plain-text body in the compose editor — CPIM
headers are generated automatically when `message/cpim` is selected. The
generated wrapper round-trips through the existing, unmodified `CpimParser`
(verified by test), so anything this client sends is parsed the same way
anything it receives already is.

## 7. Ce face Request IMDN

Adds two headers to the outbound MESSAGE request only:
`Message-ID` (fresh UUID) and
`Disposition-Notification: positive-delivery, positive-display`. This is a
**request for a future IMDN response**, nothing more — it does not generate
an IMDN document, does not implement delivered/displayed auto-responses, and
does not implement retry or offline queuing for the response (all explicitly
out of scope per the task).

## 8. Ce rămâne neimplementat

- Automatic IMDN `delivered`/`displayed` document generation in response to a received request.
- Delivery/read confirmation surfaced back into the compose UI (`Account::onInstantMessageStatus` is not wired up).
- A dedicated `Account::onInstantMessage` callback / "new message" app-level notification (inbound messages are only visible via the existing diagnostics feed).
- IMDN retry or offline queuing.
- Multiple/threaded conversations — a single flat feed (the existing diagnostics table) serves as history.
- Message persistence across restarts.
- Any MSRP capability whatsoever.

## 9. Ce este încă diagnostic-only

- MSRP: completely untouched, no session ever opened/negotiated/accepted — unchanged from Task W090.
- The Messaging Diagnostics table itself remains a read-only view; only the new "Send SIP MESSAGE" group performs an action, and that action is explicit, opt-in (checkbox-gated), and clearly separated from the diagnostics feed below it.
- `MessagingEventStore`/`MessagingDiagnosticsStore` remain pure observers — they still never send anything themselves; `SipManager`/`SipAccount` are the only new send path.

## 11. Limitări

- Send status reflects successful **submission** to PJSIP's transaction
  layer, not confirmed delivery — `Account::onInstantMessageStatus` (the
  pjsua2 callback carrying the final SIP response) is not consumed.
- No inbound "new message" application event; relies entirely on the
  existing diagnostics feed already being visible/live.
- CPIM inner content type is always `text/plain; charset=utf-8` — the
  compose body editor is plain text, so HTML-inside-CPIM composition isn't
  offered (HTML can still be sent as top-level `text/html`, just not nested
  inside a CPIM wrapper from this UI).
- A transient, non-subscribing pjsua2 `Buddy` is created and destroyed for
  every send — no presence/dialog-event side effects, but this is a
  per-message object, not a persistent contact.
- No message persistence, no per-conversation threading (matches
  `MessagingEventStore`'s existing process-lifetime-only scope).
- Inherits all Task W090/W091 parsing limitations unchanged (see
  [messaging-diagnostics.md](../messaging-diagnostics.md#known-limitations)).
